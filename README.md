# Campus Lost and Found — Secure Version

This is the secure version of my Secure Application Programming project. Students can browse and report found items, submit ownership claims, and provide a private identifying detail. Moderators can review claims and approve or reject them.

## Requirements

- Node.js 24, developed using version 24.11.0.
- npm, included with Node.js.
- Git.
- Windows PowerShell and a web browser.

SQLite is included with this version of Node.js. The application creates its tables automatically.

## 1. Download and install

For a new local copy:

```powershell
git clone --branch secure https://github.com/FelipePaneque11/campus-lost-and-found.git
cd campus-lost-and-found
npm.cmd ci
```

If the repository is already on your computer, stop any running server and use:

```powershell
git switch secure
npm.cmd ci
```

Run all commands from the folder containing `package.json`.

## 2. Configure the claim encryption key

The secure version encrypts private ownership details using AES-256-GCM. The application reads its key from the `CAMPUS_CLAIM_KEY` environment variable.

Run the following in the PowerShell terminal where you will start the server. It loads your existing key or generates one on first use, then saves it as a Windows user environment variable.

```powershell
$campusClaimKey = [Environment]::GetEnvironmentVariable("CAMPUS_CLAIM_KEY", "User")

if (-not $campusClaimKey) {
    $campusClaimKey = node -p "require('node:crypto').randomBytes(32).toString('hex')"
    [Environment]::SetEnvironmentVariable("CAMPUS_CLAIM_KEY", $campusClaimKey, "User")
}

$env:CAMPUS_CLAIM_KEY = $campusClaimKey
```

The key is 32 random bytes represented by 64 hexadecimal characters. Keep the same key while using the existing secure database. Claims encrypted with an earlier key require that key to be decrypted.

Keep the key private and outside GitHub.

## 3. Create sample items and demo accounts

Run:

```powershell
node seed.js
node seed-user.js
```

`seed.js` adds two sample items:

- Black headphones, found in the Library.
- Blue water bottle, found in the Computer lab.

`seed-user.js` creates the following accounts:

| Username | Role |
|---|---|
| `demo-student` | Reports items and submits ownership claims. |
| `demo-moderator` | Reviews pending claims and approves or rejects them. |

The script generates a separate random password for each new account and prints it in the terminal:

```text
Username: demo-student
Demo Password: <generated student password>

Username: demo-moderator
Demo Password: <generated moderator password>
```

Save these passwords privately before closing the terminal. Each password is stored in SQLite as an Argon2id hash.

### Running the seed scripts again

Existing sample IDs and usernames are preserved. If an account already exists, `seed-user.js` displays an “already exists” message.

The script only prints a password when creating an account. It cannot display or recover an existing password. Use the password saved during the first run.

## 4. Start the application

In the terminal where the encryption key is loaded, run:

```powershell
npm.cmd start
```

Open:

http://127.0.0.1:3000/

The server listens on `127.0.0.1`, port `3000`.

Press `Ctrl+C` in the server terminal to stop it.

### Starting again in a new terminal

Load the saved encryption key into the new terminal before starting:

```powershell
$env:CAMPUS_CLAIM_KEY = [Environment]::GetEnvironmentVariable("CAMPUS_CLAIM_KEY", "User")
npm.cmd start
```

The seed scripts only need to be run for initial setup or to create missing demo records.

## 5. Sign in and use the application

Open http://127.0.0.1:3000/login and enter the credentials generated by `seed-user.js`.

### Student workflow

1. Sign in as `demo-student`.
2. Report an item using its name and location.
3. Return to the home page and select **Claim this item**.
4. Enter a fictional identifying detail and submit the claim.
5. The claim is saved with a pending status.

### Moderator workflow

1. Open a separate private browser window.
2. Sign in as `demo-moderator`.
3. The application redirects to `/moderator/claims`.
4. Review the pending claims and choose **Approve** or **Reject**.

Separate browser sessions allow both accounts to be used at the same time.

## 6. Session and token configuration

### Login session

The application uses `express-session`. After successful login, the server stores the user ID and role in the session. The browser receives a cookie named `campus.sid`, which identifies that session.

The current configuration includes:

- `httpOnly: true`, preventing page JavaScript from reading the cookie.
- `sameSite: "lax"`.
- A cookie lifetime configured as 30 minutes.
- A fresh session ID after successful login.
- Session destruction and cookie removal during logout.

The session signing secret is generated automatically when the server starts. Sessions use the default in-memory store. Restarting the server requires users to sign in again.

### CSRF token

When a form page is opened, the server creates a random CSRF token for that session and inserts it into a hidden form field.

The browser sends it automatically when submitting the form. The server compares it with the session token before processing the request.

The token is handled by the application. Users do not need to generate or enter it.

### Encryption key

`CAMPUS_CLAIM_KEY` is used to encrypt and decrypt private claim details. It must remain available across server restarts.

## 7. Database location

The secure database is stored in the Windows user folder:

```text
C:\Users\<your-user>\campus-lost-and-found-secure.sqlite
```

It contains the application’s items, users, claims, and security events. Private identifying details are encrypted before insertion and decrypted for the authorised moderator response.

This database is separate from the insecure branch’s database. Demo passwords may therefore differ between the two versions.

## 8. Run automated tests

Keep the server running. Open a second PowerShell terminal in the project folder.

Install Playwright’s Chromium browser on first setup:

```powershell
npx.cmd playwright install chromium
```

Enter the student and moderator passwords generated for the secure database:

```powershell
$studentCredential = Get-Credential -UserName "demo-student" -Message "Enter the secure demo-student password"
$env:CAMPUS_TEST_PASSWORD = $studentCredential.GetNetworkCredential().Password

$moderatorCredential = Get-Credential -UserName "demo-moderator" -Message "Enter the secure demo-moderator password"
$env:CAMPUS_TEST_MODERATOR_PASSWORD = $moderatorCredential.GetNetworkCredential().Password
```

Load the saved encryption key into the test terminal:

```powershell
$env:CAMPUS_CLAIM_KEY = [Environment]::GetEnvironmentVariable("CAMPUS_CLAIM_KEY", "User")
```

Run the full suite:

```powershell
npm.cmd test
```

The test command uses one worker and the list reporter.

To run a single file:

```powershell
npx.cmd playwright test tests/search.spec.js --workers=1
```

Set the password variables again whenever you open a new test terminal.

## Troubleshooting

| Problem | What to check |
|---|---|
| `Set CAMPUS_CLAIM_KEY before starting the secure app` | Load the saved user environment variable in the terminal starting Node. |
| `Set CAMPUS_TEST_PASSWORD` | Set the student password in the terminal running Playwright. |
| `Set CAMPUS_TEST_MODERATOR_PASSWORD` | Set the moderator password in the test terminal. |
| Incorrect username or password | Use the credentials created for the secure database. |
| Invalid form token | Reopen the form and submit it again. A server restart invalidates the old session. |
| Moderator-only message | Sign in as `demo-moderator` in a separate browser session. |
| Port 3000 is already in use | Stop the other running instance before starting this version. |
| Existing claims cannot be decrypted | Check that the original encryption key is loaded. |
